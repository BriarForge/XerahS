# ES-020 temp/recovery retention and secure delete (decided 2026-11-23)

Decision ID: ES-020-RETENTION-2026-11-23
Requirement: EDITOR-SESSION-001 ES-020 (source pixels and documents are
private user data; temp and recovery files MUST follow configured retention
and secure-delete limits).
Decided by: the build loop under the maintainer's delegated owner-block
authority. No SPEC text change; the MUST stands and this record settles the
policy gate the ES-020 row named ("approved configured editor temp/recovery
retention and secure-delete limits are still an unanswered policy gate").

## Question

What are the configured limits, their defaults and bounds, and what does
"secure delete" honestly mean for the editor's private temp and recovery
files?

## Research

- The behavioural reference (ShareX, CleanupManager.cs + ApplicationConfig.cs,
  read directly): the whole ShareX temp folder is deleted at every startup;
  beyond that, cleanup is opt-in and count-based - `AutoCleanupBackupFiles`
  and `AutoCleanupLogFiles` both default false, `CleanupKeepFileCount = 10`
  keeps the newest files by write time. The reference has no age-based
  retention and no secure delete at all.
- GNU coreutils `shred(1)` (fetched from man.archlinux.org, coreutils 9.12,
  2026-11-23): "CAUTION: shred assumes the file system and hardware
  overwrite data in place. Although this is common, many platforms operate
  otherwise. Also, backups and mirrors may contain unremovable copies that
  will let a shredded file be recovered later." Overwrite-based secure
  deletion is therefore a best-effort reduction, never a promise.
- This edition's own invariant (EditorTemporaryFiles.h, landed earlier):
  "Unlink is best effort deletion, not a promise of physical erasure on
  SSD/COW storage." Temp files already live only in a 0700 owner-verified
  directory with 0600 files; recovery records in the XDG state directory are
  owner-private with per-file locks and exited-owner gating.

## Decision

Three profile-scope settings under the General section carry the limits:

- **`editorRetention.temporaryDays`** - default 1 (today's 24 h sweep made
  configurable), integer 0..30. The startup sweep unlinks abandoned
  preparation/upload files older than the bound; 0 sweeps every startup,
  which is the reference's own startup-clean, and stays safe on POSIX
  because an in-flight task's open handle survives unlinking.
- **`editorRetention.recoveryDays`** - default 7, integer 0..90; 0 keeps
  today's count-only behaviour. The startup sweep prunes records whose owner
  has exited and whose `savedAt` is older than the bound, using the store's
  existing per-file lock, exited-owner and valid-document pattern; a live
  owner's record is never an age candidate, exactly as the count prune
  already refuses it. The existing count bound (kMaxRecords) stays.
- **`editorRetention.secureDelete`** - default off, matching the reference
  (which never overwrites). When on, both sweeps overwrite the file with
  one zero-fill pass, fdatasync, then unlink. The settings page states the
  shred-documented caveat: overwrite reduces recoverability where the
  filesystem overwrites in place, and is not a guarantee on SSD/COW or
  mirrored storage.

Retention limits are enforced at startup (after the settings store loads,
so the configured values govern the sweeps) and the sweeps never touch
anything the private-directory checks have not verified as this user's own
regular file.
